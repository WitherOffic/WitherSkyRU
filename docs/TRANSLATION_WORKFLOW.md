# WitherSkyRU — постоянный регламент разработки

Регламент действует для последующих ручных и автоматических этапов перевода, исправления ошибок, оптимизации и сборки. Он описывает работу, но сам по себе не запускает расписание и не устанавливает мод. Прямые указания пользователя определяют разрешённый объём текущей задачи.

## 1. Источники состояния и исходная точка

При каждом запуске прочитайте [AGENTS.md](../AGENTS.md), актуальную точку возобновления в [DEV_STATUS.md](DEV_STATUS.md) и [BUGS.md](BUGS.md). Используйте этот регламент; затем открывайте только материалы выбранного этапа. История старого диалога не нужна.

Состояние на момент введения регламента, 2026-10-21:

| Объект | Исходное состояние, не вечная константа |
| --- | --- |
| Рабочая копия | Путь из DEV_STATUS, `work/minecraft-26.2/WitherSkyRU` |
| Ветка / HEAD | `feature/minecraft-26.2` / `8a65e62f768b2ee863e60a324de743dc695dfdf9` |
| Версия | `0.16.0-dev`, Minecraft 26.2, Fabric, Java 25 |
| Последняя принятая партия переводов | 115; миграция на 26.2 завершена отдельно |
| Незавершённые материалы | Редакторские материалы 117, ещё не импортированные как новая партия |
| Первые источники для продолжения | `translation-source/FIVE_PASS_117_REVIEWED.json`, затем `ABIPHONE_REQUIREMENTS_117_REVIEWED.json`; дополнительные источники — по указателю в DEV_STATUS |
| Историческая фиксированная очередь | 16 244 строки, 13 984 отдельных точных ключа, 2 260 без точного ключа; источник — `translation-source/NPC_PROGRESS_0.15.115.json` |

Эти числа не описывают всю игру. Остаток без точного ключа может включать уже работающие шаблоны. Заявленные в старом отчёте 141 черновик не считайте заново подтверждённым общим количеством без полного доступного списка и дедупликации. Два перечисленных файла не заменяют весь архив аудита 117.

После каждого этапа главным указателем становится новый checkpoint в DEV_STATUS. Если branch, HEAD, версии или состав изменений расходятся с ним, сначала объясните расхождение. Не заменяйте актуальную разработку старой `main` и не начинайте массовое восстановление по памяти.

## 2. Один запуск — один ограниченный этап

По умолчанию выбирайте один тип работы: разбор ошибок, небольшая партия перевода, одна оптимизация либо контрольная сборка. Не объединяйте миграцию, массовую редактуру и изменение движка в один этап.

| Ограничение обычного автоматического запуска | Правило |
| --- | --- |
| Объём перевода | 1000 новых уникальных исходных строк на партию по прямому указанию пользователя; уже принятые строки и числовые варианты одного шаблона не увеличивают счётчик |
| Оптимизация / ошибка | Одна подтверждённая причина и связанные с ней изменения |
| Время | Конечная партия 1000 строк; сохранять курсор после внутренних порций, резервировать время на проверки/checkpoint; не завершать каждую десятку отдельным отчётом или JAR |
| Повтор команды | Один первоначальный запуск и не более одного повтора после конкретного исправления причины |
| Завершение | Один итоговый отчёт, состояние файлов и точная следующая операция |

Это рабочие пределы, а не обещание, что инструмент принудительно остановит процесс. Исполнитель обязан контролировать время и таймауты дочерних процессов. Долгую сборку, расширенную регрессию или игровое измерение оформляйте отдельным этапом с конечным бюджетом. Не начинайте дорогую команду, если для неё и сохранения результата не осталось времени. Внешний лимит токенов учитывайте, если он доступен; численную стоимость или расход без данных не выдумывайте.

Порядок запуска:

1. Установить реальный корень через `git rev-parse --show-toplevel`; сверить `git branch --show-current`, `git rev-parse HEAD`, `git status --porcelain=v1 -uall` и текущую версию с DEV_STATUS.
2. Проверить BUGS: критические открытые ошибки имеют приоритет; остальные добавить в ближайший подходящий этап.
3. Получить общую блокировку изменений и повторно сверить состояние после её получения (раздел 3).
4. Найти последнюю незавершённую операцию и предыдущий отчёт. Проверить, не сделана ли она уже по ID, diff и результатам проверок. Не повторять выполненную редактуру или импорт.
5. Записать ID запуска, партию, небольшой список ключей/цель, разрешённые пути, исходные хеши затрагиваемых файлов и критерий готовности. Сохранить checkpoint «В работе» до первой содержательной мутации.
6. Выполнить только этот этап и необходимые проверки. Если не хватает контекста или среды, сохранить точную причину и сделать независимую разрешённую работу, когда она есть.
7. Сохранить единый отчёт, обновить DEV_STATUS, сверить diff/status, освободить свою блокировку и завершиться. Не запускать следующий этап в том же автоматическом вызове.

Ручной запуск использует те же правила состояния, защиты чужих изменений и отчёта; увеличение объёма допускается прямой задачей пользователя.

## 3. Защита от параллельных изменений и повторов

**Один писатель на репозиторий.** Все ручные и автоматические исполнители, меняющие этот проект, используют одну блокировку; разные worktree не разрешают конкурировать за версии, журнал и очередь.

- Местоположение блокировки: файл `witherskyru-development.lock` внутри абсолютного `git rev-parse --path-format=absolute --git-common-dir`. Он находится вне поставляемого исходного кода и общий для worktree одного репозитория.
- Получать её нужно атомарным эксклюзивным открытием файла, например через .NET `File.Open` с `FileMode.OpenOrCreate`, `FileAccess.ReadWrite`, `FileShare.None`. Проверка `Test-Path` с последующим созданием не является блокировкой. Само существование файла также не означает занятость.
- Эксклюзивный дескриптор удерживается живым процессом весь этап: изменения, тесты, отчёт, DEV_STATUS. Закрытие оболочки, которая открыла файл, освобождает блокировку; нельзя получить её отдельной короткой командой и считать дальнейшие команды защищёнными. Исполнитель должен обеспечить постоянного владельца и контролировать его жизнь.
- Если инструмент не умеет удерживать такую блокировку, изменяющий автоматический запуск не выполнять: сообщить о недоступном механизме, оставить только чтение. Этот документ не является уже установленным процессом блокировки.
- При занятой блокировке закончить запуск с `SKIPPED_BUSY`, не ждать в цикле, не менять BUGS/DEV_STATUS/версии. Отчёт дать в чате; общий файл отчёта записать только при безопасном доступе позже. Не удалять чужой lock и не убивать чужой процесс.
- При штатном завершении закрыть только свой дескриптор в `finally`; lock-файл можно оставить. После аварии ОС освобождает дескриптор; проверить сохранённый checkpoint и незавершённую операцию, а не удалять данные вслепую. На разных компьютерах эта блокировка не общая: назначить одного активного писателя либо согласовать отдельную общую координацию до запуска.

Сохраняйте исходные отслеживаемые и неотслеживаемые изменения. Известные незакоммиченные файлы из checkpoint допустимы: требование «всегда чистое дерево» ломает продолжение. Сверяйте также их содержимое/хеши; совпадение списка путей недостаточно. При неизвестных изменениях в нужном файле или неожиданной смене HEAD остановите затронутую запись, опишите конфликт и сохраните независимые результаты. Повторно сверяйте ожидаемое содержимое непосредственно перед записью и итоговый diff после неё; блокировка не защищает от редактора, который не соблюдает протокол.

Не применять без разрешения `reset`, `clean`, `checkout`, `switch`, автоматический stash, перезапись чужих файлов или массовое форматирование. Не создавать параллельных агентов-писателей. Не делать commit/push, публикацию, установку JAR или смену ветки только потому, что завершена партия; для этих действий нужна соответствующая задача.

Для идемпотентности храните в отчёте и checkpoint стабильный ID партии, ID записей, хеш источника, выполненные шаги и ожидаемые следующие шаги. Запись идентифицируется корпусом, поверхностью вывода, точным исходником и контекстом; порядковый индекс — лишь дополнительный указатель. Терминальные исходы: принята, уже покрыта, отклонена с причиной. Отложенная запись остаётся в явном списке с условием возврата. При следующем запуске продолжайте с первой незавершённой операции, не импортируйте её повторно.

Повторяющийся блокер получает fingerprint: причина + нужные входные файлы/их хеши + ошибка среды. При неизменном fingerprint не запускать снова те же поиск, тест или сборку. Один раз сообщить, сохранить условие разблокировки и переключиться на независимую задачу либо закончить запуск. При исчерпании очереди закончить с `NO_WORK`, без создания фиктивной партии или версии. Не планировать себе дополнительные немедленные запуски, бесконечный goal или собственный цикл продолжений.

## 4. Продолжение перевода и контроль качества

Продолжайте материалы 117 после принятой партии 115; не импортируйте весь архив одним действием. В новом ID этапа используйте, например, `review117-001`, затем следующий свободный номер. Номер этапа независим от dev-версии мода. Текущий cursor и результат предыдущего этапа берите из DEV_STATUS.

Для каждой выбранной записи:

1. Сохранить точный исходник, авторский перевод, персонажа/экран/поверхность, источник и его ревизию/дату. Уточнить, является ли текст актуальным серверным, архивным, alpha или описанием стороннего руководства. Выдержка из wiki, история задания и фанатское предложение имеют разный статус. При внешнем подтверждении открыть первичный источник, не ограничиваться поисковой выдачей.
2. Проверить, отсутствует ли перевод на самом деле: точный ключ, допустимая нормализация движка, существующий шаблон, порядок провайдеров и реальный hook. Отсутствие точного ключа в `rg` ещё не доказывает отсутствие перевода в игре. Запись в файле, который не загружается, не считается подключённой.
3. Проверить соседние фразы и цель действия. Согласовать термины с принятыми runtime-таблицами; спорное решение кратко записать в отчёт со ссылкой на существующий термин. Не переводить имя/предмет непоследовательно в рамках одной цепочки.
4. Проверить естественность русского, обращение, падежи, род, число, пунктуацию и длину в интерфейсе. Сохранить числа, единицы, уровни, значки, команды, ID и ссылки. Предписанную заданием буквальную английскую фразу для ввода оставить исходной.
5. Сверить дубликаты по точному source и нормализованному ключу, который действительно использует движок. Не удалять значимые знаки препинания, форматирование или границы сообщений ради объединения. Одинаковый русский текст при разных английских ключах сам по себе не ошибка; разные переводы одного ключа — конфликт для разбора. Не полагаться на JSON-парсер, молча перезаписывающий повторённые ключи объектов.
6. Для шаблона определить закрытое семейство, допустимые диапазоны чисел/римских уровней, множественность переменных и границы. Проверить минимумы/максимумы, ноль/единицу/множественное, недопустимые и слишком длинные входы, пересечения с точными ключами. Не превращать произвольный текст игрока в переводимую переменную и не перечислять все значения заранее.
7. Проверить компоненты, смысловые цветные участки, текущий шрифт, click/hover/insertion, timestamps, счётчики и варианты разбиения текста. Эталон русской фразы должен быть авторским, независимым от вывода самой реализации. Добавить проверки overrides и отрицательные примеры игрока/подписанного чата/ввода.
8. Подключить только готовую запись в реально загружаемый ресурс. Подтвердить ожидаемый полный текст и сохранение оформления через соответствующий runtime-путь. Если это пока редакторская проверка, оставить статус черновика/ожидания runtime-проверки и не увеличивать число принятых переводов.

Не снимать защиту неизвестных стилей ради процента. Исторические эталоны не переписывать под новый результат; оправданные изменения ожиданий оформлять отдельно и явно. Авторские материалы, происхождение и независимые ожидаемые значения сохранять вместе с партией, а не только в build.

## 5. Постепенная оптимизация и сохранение функций

Оптимизируйте один подтверждённый горячий путь за этап. Начните с воспроизводимого сценария и замера «до», затем меняйте код и измеряйте «после» при равной полезной работе. Уменьшение числа переведённых строк, отключение Mixin или урезание защиты не является оптимизацией.

| Что сравнивать | Как фиксировать |
| --- | --- |
| Работа переводчика | Время операции, allocations/op, попадания/промахи кэша на одинаковом наборе входов |
| Плавность в игре | Frametime median/p95/p99, частота длинных кадров; FPS и 1%/0,1% low — только при достаточной серии кадров и указанной методике |
| Память | Heap после одинакового прогрева/нагрузки, retained size при доступности профайлера, паузы/частота GC, рост кэшей |
| Условия | Minecraft/Java, JAR SHA-256, моды/версии, ресурспак, настройки, сцена/маршрут, длительность, прогрев, оборудование и фоновые нагрузки |

Запускайте бенчмарки последовательно, отдельно от тестов, сборки и игры; используйте порядок A–B–B–A с повторами. Сохраняйте все сырые серии и разброс. Различайте новый полезный перевод и прежнюю равную нагрузку. Не объявляйте улучшение по одному удачному замеру и не выдавайте микробенчмарк за игровые FPS. Если среды нет, пишите «не измерено» и оставляйте игровую проверку отдельной задачей.

При воспроизводимом ухудшении времени/аллокаций разберите причину; ориентир проекта «более 5% в обоих порядках» — сигнал расследования, а не гарантия отсутствия меньшей деградации. Для frametime/памяти указывайте абсолютные значения и относительную разницу с учётом шума. Не обещайте нулевое влияние, отсутствие всех утечек или устранение микролагов без соответствующих измерений.

Сохраняйте офлайн-перевод; никаких сетевых переводчиков, дискового I/O, полного прохода словаря на кадр, неограниченных кэшей и дорогих regex без границ. Кэшируйте неизменяемые планы, не текущие компоненты/стили/мир; проверяйте ограничения, lifecycle и восстановление scopes при исключениях.

Защитные проверки выбирайте по затронутой функции: GUI/HUD и размеры панелей; tooltip/переносы/Inter/Shift; NPC/системные сообщения и переключатели; русский/английский поиск; overrides; сохранение/отмена настроек; защита имени игрока/ввода/F3/подписанного чата; серверный gate; действующие внешние мосты. Не менять исходный ItemStack, серверные данные и исходную историю сообщений. Для новых версий сторонних модов нужны байткод и проверка реальных вызовов, не просто зелёная компиляция.

## 6. Тесты и периодическая сборка JAR

Выбирайте минимальные достаточные проверки по риску. Для новых runtime-переводов нужны независимые ожидаемые тексты и релевантные регрессии. Для простой правки Markdown достаточно проверки ссылок, согласованности и diff; тесты мода из-за неё не запускать.

| Этап | Доступная проверка / условие |
| --- | --- |
| Материалы 117, целостность переменных и чисел | `python -X utf8 -m unittest discover -s tests -p 'test_five_pass117.py' -v`; это не проверка runtime-перевода и не литературный редактор |
| NPC literal / числовые формы | `./gradlew.bat verifyTestNpcLiterals115 verifyTestNpcNumbers115` плюс независимые проверки новой партии |
| Защита текста, поиск, HUD, кэши, настройки | Соответствующие `verifyTestPlayerTextProtection`, `verifyTestRussianSearch`, `verifyTestHudLayout`, `verifyTestPerformanceCaches`, `verifyTestTooltipFont`, `verifyTestInteractionModes` |
| Контрольная сборка | `./gradlew.bat build`; включает четырнадцать main-based наборов, не JUnit discovery |
| Полная Python-регрессия, когда затронуты инструменты/извлечение | `python -X utf8 -m unittest discover -s tests -p 'test_*.py' -v` |
| Расширенная регрессия / внешние мосты | Команды и ограничения из DEV_STATUS и `MIGRATION_26_2_RU.md`; запускать при затронутой области и доступных архивных fixtures |
| Игровой smoke | Отдельный `clientSmokeTestJar` и запуск по DEV_STATUS; успешная сборка не равна успешному запуску Minecraft |

Указывать точную команду, дату, версию/хеш проверенных входов, exit code, PASS/FAIL/NOT_RUN/BLOCKED и путь к доступному результату. Количество выполненных тестов брать из свежего вывода, не из старого отчёта. Пропущенный из-за отсутствующей среды набор отмечать явно; недостающие fixtures не повод удалять проверки. Нужен повтор только после изменения входов/исправления причины; не гонять весь архив по каждому ключу.

**Периодичность JAR:** после изменения runtime-кода/маршрутизации и исправления серьёзной ошибки — отдельный ближайший этап сборки до признания кандидата готовым. Для небольших принятых ресурсных партий — не реже каждой третьей партии либо семи дней с первой несобранной партии, что наступит раньше, если есть изменения. Это триггер создания конечной задачи, а не разрешение превысить бюджет текущего запуска. Документация, пустой запуск и чистая редакторская проверка не требуют нового JAR. Число несобранных партий и время первой хранить в checkpoint.

Перед сборкой выполнить правила версии (раздел 7). `clean` применять только при необходимости, предварительно сохранить нужные доказательства и принятый JAR вне удаляемого build. На успехе проверить metadata и ресурсы внутри JAR, отсутствие тестового драйвера, размер и SHA-256. Указать commit и fingerprint незакоммиченного diff, если JAR собран из изменённого дерева. Предыдущий принятый артефакт не перезаписывать; не устанавливать в пользовательскую сборку и не публиковать автоматически.

## 7. Последовательные dev-версии без повторов

Принятая схема: `0.15.115-dev` до миграции, `0.16.0-dev` для 26.2. В текущей линии продолжать **`0.16.N-dev`** с увеличением третьего компонента; ближайший кандидат при введении регламента — `0.16.1-dev`, только если номер ещё свободен. Не возвращаться к `0.15.116-dev`, не называть версию просто «117» и не вводить параллельную схему `dev1`/дат без отдельного решения о версии.

1. Под общей блокировкой сверить `build.gradle`, `src/main/resources/fabric.mod.json`, журнал версий/checkpoint DEV_STATUS, локальные refs/tags и изменения этих двух metadata-файлов в доступной Git-истории. Проверить известные имена JAR в `build/libs` и явно указанном каталоге доставки. Не обходить весь диск и не считать произвольные версии зависимостей версиями мода.
2. Выбрать следующий номер выше максимального занятого/зарезервированного в линии `0.16`. Если встречен пробел, не заполнять его повторно. При известном внешнем писателе/непроверенной публикации сперва согласовать состояние; офлайн-проверка локальных refs не доказывает отсутствие чужого remote-релиза. Не выполнять незапрошенные fetch/push ради каждой партии.
3. До первого изменения metadata добавить строку в постоянный журнал версий в DEV_STATUS: номер, run ID, дата, состояние `reserved`, основание. Синхронно обновить обе версии. При аварии сначала проверить эту резервацию и реальные артефакты.
4. Одну зарезервированную версию можно доработать несколькими этапами до первого сохранённого JAR, связывая их с одним кандидатом. После появления сохранённого/переданного JAR этот номер навсегда занят: новое содержимое получает следующий. Не заменять уже существующий JAR другим содержимым под тем же именем.
5. Состояния журнала: `reserved` → `built` → `accepted`; окончательно прекращённый кандидат — `failed`/`abandoned`, его номер не переиспользовать. Если работа лишь приостановлена после ошибки и JAR ещё не сохранён, оставить `reserved` с результатом проверки и cursor: это продолжение того же кандидата, не новая выдача номера. Не удалять строки неудачных резерваций ради «красивой» последовательности.
6. Разделять текущую версию исходников/кандидата и последний проверенный JAR: при неудачной сборке последний рабочий артефакт не становится новой версией. Проверить совпадение version в metadata JAR, имени файла и отчёте.

В этапе только документации версии не повышать и номер не резервировать. Успех тестов без сборки не выдавать за готовый JAR.

## 8. Измеримый учёт перевода

Каждый счётчик должен иметь корпус, неизменный способ подсчёта, путь к данным и их хеш/ревизию. Для поэтапного реестра сохраняйте ID записи, source, контекст/поверхность, перевод, происхождение, статус, literal/template, проверку подключения, тесты и run ID последнего изменения. Реестр заводится/дополняется по мере обработки, а не путём выдуманной полной классификации старой базы.

| Показатель одного полностью классифицированного корпуса | Определение |
| --- | --- |
| N — известно | Уникальные строки зафиксированного корпуса после объявленной дедупликации |
| T — переведено и принято | Полный перевод подключён и прошёл нужные проверки, с доступными доказательствами |
| D — черновики | Есть целевой текст, но не завершена редактура/подключение/приёмка |
| U — без перевода | Нет принятого перевода и нет черновика |
| V — проверено | Уникальные записи с завершённой указанной проверкой и доказательствами; вид проверки обязателен |
| E — точные ключи | Строки с отдельной точной runtime-записью, отдельная историческая метрика |

При полной классификации `N = T + D + U`, остаток до приёмки `R = D + U`. V — пересекающийся показатель, не четвёртая категория; редакторская и runtime-проверка показываются раздельно. Если классификация частичная, указать количество неклассифицированных, а не записывать его в U. Статусы отклонённых источников и защищённого буквального ввода выводить отдельно, исключать из знаменателя только при явной новой версии корпуса с объяснением.

`100 × T/N` — покрытие принятого перевода **конкретной известной базы**, если T известно. `100 × E/N` — покрытие её точными ключами; эти показатели не взаимозаменяемы. Для старой очереди из `NPC_PROGRESS_0.15.115.json` достоверен исторический E/N; текущие T/D/U/V по всем 16 244 строкам из этого файла не выводятся. Не называть 2 260 строк «точно непереведёнными» и не прибавлять количество шаблонов/числовых комбинаций к числу точных ключей.

Числа текущего запуска вычислять из уникальных обработанных ID и сохранённых переходов статусов. Отдельно показывать просмотрено, проверено редактором, принято в runtime, исправлено существующих переводов, уже покрыто/дубликаты, отложено и отклонено. Не считать повторы одного теста или строки дважды. Число «переведено за запуск» не равно числу просмотренных черновиков.

Динамика: для того же корпуса и методики `ΔX = X_now − X_previous`, разница процентов — в процентных пунктах. При первом запуске либо отсутствии сравнимого снимка — `н/д: нет предыдущего снимка`. При новом корпусе показать старый и новый знаменатель отдельно; не рисовать искусственный скачок прогресса. Исторический показатель сопровождать датой и пометкой «не пересчитан сейчас». Неизвестные значения — `н/д`, никогда не произвольные нули.

**Полоса ровно 20 символов:** `filled = floor(20 × value / N)`, затем `█ × filled + ░ × (20 − filled)`, процент округлять отдельно до двух знаков. Проверить `0 ≤ value ≤ N`. Образец формы: `████████░░░░░░░░░░░░`; он не является фиксированным значением. Для недоступных данных/N=0 — «полоса не рассчитана: причина», без ложных 0% или 100%. Исторические 13 984/16 244 дают `█████████████████░░░` и 86,09% точных ключей старой очереди, а не всей игры.

## 10. Ошибки со скриншотов и очередность работ

Каждый запуск, включая автоматический, проверяет [BUGS.md](BUGS.md). Изображение пользователя — основание для диагностики и регистрации, но не доказательство конкретного дефекта кода или падения FPS.

1. Изучить доступное изображение: видимый неверный текст/цвет/обрезка/расположение, GUI/HUD/tooltip, выбранный предмет, экран/локация/событие, отображаемые показатели. Отделить наблюдение от гипотезы. Не утверждать, что изображение просмотрено, если оно недоступно.
2. Запросить только недостающее для воспроизведения: например, исходную строку, версию JAR/модов, действие, ожидаемый результат, сервер/экран или замер frametime. Не просить весь конфиг, аккаунт или журнал без необходимости. Остальную независимую работу продолжать.
3. Под блокировкой зарегистрировать новый свободный `WSRU-NNNN` или дополнить существующий дубликат. Записать приоритет, статус, наблюдение, шаги, ожидаемое/фактическое, затронутую функцию и доступное доказательство. Ссылку давать только на реально доступное вложение/файл. Если URL/файла нет, написать «вложение сообщения пользователя; локальный файл и постоянная ссылка недоступны». Не выдумывать путь и не обещать сохранённый скриншот.
4. Точечно проверить соответствующий словарь/код и реальный путь вывода. Для неподтверждённой причины сохранить гипотезу; не устранять её случайной заменой или отключением функции. Подтверждённую причину исправить минимально, добавив оправданную регрессионную проверку.
5. Выполнить доступные проверки. Если нужна визуальная/игровая проверка, статус — **«Ожидает проверки в игре»**, даже при успешных автоматических тестах. Не писать «Исправлено окончательно» по компиляции или одному скриншоту.
6. После конкретного подтверждения пользователя или воспроизводимого игрового прогона на нужной версии записать результат и закрыть. При воспроизведении снова открыть тот же ID, сохранив историю.

P0/P1 обрабатываются перед следующей runtime-партией перевода/сборкой. Если критическая ошибка заблокирована ожиданием игры/данных, указать это в checkpoint: не выпускать затронутый кандидат и не повторять бесполезную диагностику. Независимая редакторская работа допустима с явным ограничением. P2/P3 включать в ближайший связанный этап, не останавливая весь перевод без причины.

Не публиковать личные данные со скриншотов: имена/UUID/чат/адреса/личные координаты и любые чувствительные сведения исключать из публичных записей; в цитатах использовать безопасные плейсхолдеры. Оригиналы и частные логи хранить только в действительно доступном приватном месте, при необходимости в уже игнорируемой `.migration/bugs/`, и проверять Git status. Публичную копию можно добавлять лишь после фактического обезличивания, визуальной проверки и соответствующего разрешения на публикацию. Путь в BUGS тоже не должен раскрывать личные данные. Публичные записи содержат минимальную техническую информацию, не OCR-дамп всего экрана.

В каждом отчёте раздел «Ошибки» вычислять из карточек журнала. Открытые — все нетерминальные статусы; ожидание игры — их подмножество; критические — открытые P0/P1. Исправлено за запуск — число ID, получивших подтверждение исправления и статус «Закрыта» именно в этом запуске. «Дубликат» и «Не воспроизведена» не считаются исправлениями. Подготовленные исправления в ожидании игры показывать отдельно.

## 11. Обязательный checkpoint DEV_STATUS после этапа

Обновлять состояние после каждого завершённого/частичного этапа, включая провал проверки; незавершённый этап тоже должен иметь точку продолжения. Не затирать историю происхождения кода и ещё действующие ограничения. Не утверждать, что статус уже сохранён, пока запись не выполнена.

Минимальные поля:

- Run ID, время/часовой пояс, вид работы и результат; ссылка на единый отчёт и предыдущий сравнимый отчёт.
- Последняя принятая партия; текущая незавершённая партия, источник/хеш, обработанные ID, pending/deferred с причиной; cursor следующего действия, а не только «продолжить перевод».
- Branch, HEAD, исходный и конечный status, происхождение известных незакоммиченных файлов. Fingerprint изменённых данных/результатов; при неожиданной чужой записи не перезаписывать checkpoint без согласования.
- Версия исходников, журнал занятых dev-номеров, последний принятый JAR и его SHA-256; reserved/failed отдельно. Количество несобранных runtime-партий и дата первой.
- Счётчики с корпусом/методикой/путями и доступностью данных; предыдущий снимок для динамики, неизвестные значения явно неизвестны.
- Реально выполненные команды, итоги, доказательства, что пропущено и почему; точная следующая проверка.
- Открытые критические BUGS, подготовленные исправления и ожидание игры; блокеры/fingerprint/условие разблокировки.
- Одна следующая ограниченная задача. Секретов, личных журналов и оригиналов приватных изображений в checkpoint быть не должно.

При commit в будущем обновить записанные Git-сведения с учётом того, что документ не может содержать собственный будущий хеш: указать проверенный базовый HEAD и явно отметить, что документ включён в следующий коммит; фактический HEAD перепроверить при старте.

## 12. Экономия контекста и включение автоматизации

Не перечитывать весь проект, старую переписку и все исторические отчёты. Использовать `rg`, небольшие диапазоны и карту архитектуры DEV_STATUS; сохранять найденный путь, терминологическое решение и результат, чтобы следующий запуск их не открывал заново без изменения входов. Один ограниченный проход по runtime-словарям для дедупликации партии допустим; полный аудит репозитория на каждом запуске — нет. Не переписывать исторические генераторы отчётов только ради оформления новой партии.

Автоматизация предлагается как повторяющееся продолжение **этого чата** (heartbeat), один запуск в сутки, например **11:00 Asia/Novosibirsk**. Это предложенное время, не уже включённое расписание.
